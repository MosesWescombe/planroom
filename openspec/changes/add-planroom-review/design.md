## Context

Planroom already has two session kinds, `plan` and `ask`, and planroom-ask (9f86c33) showed what adding a kind costs: `SessionKind` is the key of the `TOOLS`, `SERVER_NAMES` and `INSTRUCTIONS` maps in `src/server/mcp.ts`, of `PLANROOMS` in `src/server/install.ts` and of the `--ask` flag in `src/cli.ts`, with `Session.openAsk`, `askDir`, an ask-only event gate and `view.kind` branches in Shell, Rail, TopBar and PhaseTabs. Blocks, the event log and `planroom_wait`, channel push, comment threads, themes and the PDF and HTML export are shared. See proposal.md for why.

The CLI is bundled by Vite, so the `diff` package the page already uses can be used by the server-side poster without a new runtime dependency.

## Goals / Non-Goals

**Goals:**

- Add the review kind on the existing seams, with no new plugin layer.
- Run the same pure derivation, from reactions to comments with the sign-off rule applied, in the page preview and in the server poster, so what is posted is what was previewed.
- Keep code, diffs and credentials on the machine: pictures are drawn by the agent, and only approved comments and tasks go to Bitbucket.

**Non-Goals:**

- GitHub (Q-2): the posting model differs (one atomic review object), and the user's repos are on Bitbucket.
- Approve or request-changes verdicts: Q-1 did not select them.
- A hard PR size limit in v1: large diffs keep the 6 to 15 slide spine and are grouped by area.
- Importing another tool's review output: none of the candidates keeps per-finding state a reviewer can react to.
- Changing the plan and ask sessions beyond the shared block catalog (`analogy`, `stepThrough`, wider `compare`).

## Decisions

1. **A third tool in this package, on the same seams as ask (Q-3, Q-4).** Review becomes `SessionKind = plan | ask | review`, with its own skill, server (`planroom mcp --review`), page and `.planroom/reviews/<id>/` folder (id `pr-<number>` or `branch-<name>`), and the tool and instruction maps extended in place. Rejected: a separate package, because the block catalog, event log, threads and export are shared and would be duplicated or published as a fourth package; and a generic plugin layer, because there are three kinds and a registry would be built for no fourth.
2. **Bitbucket Cloud and local branches only (Q-2).** The Bitbucket client is a small fetch wrapper with basic auth, typed responses and retry on 429, tested with a fake client. Rejected: GitHub as well, whose atomic `POST /pulls/{n}/reviews` is a different posting model that would double the poster and preview work for a host the user does not use.
3. **A temporary git worktree at the PR head (Q-5, Q-39).** A worktree manager adds, moves and removes a worktree under the review folder. Rejected: reading the reviewer's checkout, which may be on another branch with uncommitted work; reading files through the provider API, which is slow and cannot trace callers across the tree; and a full clone, which costs time and disk for what a worktree gives.
4. **The tool runs its own review: reviewers plus a verify pass, at a strength the reviewer picks (Q-6, Q-23).** `planroom-reviewer` runs for correctness, security, performance, design fit and tests, and a verify pass told to refute drops what it cannot confirm. Five reviewers and a verifier used far too many tokens on a trial PR, so the reviewer picks `single` (one reviewer that verifies itself), `standard` (one reviewer and a verifier, the default) or `thorough` (one per dimension and a verifier), and the subagents' model and effort, on a card the page shows as each round opens, pre-filled from Settings. The agent starts no reviewer before the `reviewers.start` event, and the round records the choice. Rejected: importing `twg-code-review`, which needs a machine-specific binary, and the `code-review` plugin or caveman-review, which keep no per-finding state, so any import would be remapped into the page's shape anyway; and any strength with no verify step at all, whose false positives would be posted under the reviewer's name.
5. **Agent-drawn SVG illustrations (Q-7, Q-24).** The main agent writes the deck, as one voice and one story, and briefs a `planroom-illustrator` subagent that draws SVG into `assets/` in parallel. SVG is shown through the `image` block under a `sandbox` CSP, so SMIL and CSS animation plays and scripts do not. Rejected: an image-generation service, which would send code to a third party; and one agent drawing and writing, which serialises the slow part.
6. **A typed deck of catalog blocks plus new blocks and an html escape hatch (Q-8, Q-20).** Slides are made of catalog blocks, `analogy`, `stepThrough`, `yourTake` and a wider `compare`, with `html` for the rare interactive visual. Rejected: free-form agent HTML for every slide, which would give up the validation, theming, export and review behaviour blocks already have.
7. **`analogy`, `stepThrough` and the wider `compare` join the shared catalog; `yourTake` and `html` are review-only (Q-20; assumption in the write-up).** Planning and asks gain the three general blocks, and the other two are refused outside a review the way plan-only events are refused in an ask. Rejected: making all five review-only, which would leave planning without blocks it benefits from; and allowing all five everywhere, since a prediction card makes no sense in a write-up and `html` widens the attack surface of every session.
8. **Slides are staged and published in two parts (Q-22, Q-36).** `slide.upsert { id, chapter, order, title, blocks }` stages a slide; the first `deck.publish` releases Why to What it might impact and the second, once the reviewer has sent their concerns on the impact map, releases Trade-offs. Each part is fixed for the round once published. Meanwhile the page shows progress. Rejected: streaming slides as they are written, because the deck is meant to be cohesive and a reader could finish a slide the agent then rewrites.
9. **One slide at a time with an overview grid, a fixed four-chapter spine (Q-19, Q-21).** Why, How it works, What it might impact and Trade-offs at about 6 to 15 slides. What it might impact is one slide with an impact map: areas the change might reach, each opening its explanation and a box for the reviewer's concerns, which reach the agent when they move on; Trade-offs is written after, answering every concern beside the agent's own trade-offs. Rejected: a fifth chapter beside What it touches, which would mostly repeat it; and answering concerns in the Review tab, which keeps them out of Trade-offs. Step-throughs take the arrow keys first. Motion is CSS transitions, the View Transitions API and step-through state with no animation library, and stops under `prefers-reduced-motion`. Rejected: a scrolling page, which loses the pacing the your-take cards depend on; and a library such as framer-motion, which a few CSS transitions replace.
10. **Your-take cards log the answer, then reveal (Q-9, Q-10).** Four kinds, with the agent's view written when the slide is made and held back until the answer is logged. The findings follow the same rule at review scale: the Review tab is locked until the walkthrough is finished or skipped, and a skip is logged. Rejected: showing findings alongside the walkthrough, which lets the reviewer nod along; and a hard lock with no skip, which blocks a reviewer who already knows the PR.
11. **Preferences in Settings, saved per machine in `$XDG_CONFIG_HOME/planroom/review.json` (Q-10, Q-13, Q-34).** A preferences store module reads and writes it, `planroom_review` and `planroom_state` hand it to the agent, a prompt change applies to slides not yet written and a view change applies at once. Rejected: `localStorage`, which is per port and so would reset between sessions; and per-review settings, which the reviewer would repeat for every PR.
12. **Findings are issues, design opinions and questions with five views (Q-11, Q-13).** Pins on the deck's diagrams, cards beside the diff, `bar` charts, a `fileTree` heat map and a `riskMatrix`, each switchable. Most reuse existing blocks, and the new work is a badge overlay on the diagram renderers and anchored cards in the code viewer. Rejected: a flat findings list, which hides where in the design a finding lives.
13. **Agree, Reword or Reject on every finding, with a thread first (Q-12).** Agree queues the draft, Reword the reviewer's text, and Reject queues nothing but sends its reason to the agent. Rejected: reacting only to what the reviewer wants to post, which gives the agent no signal about its false positives.
14. **Comments are derived once, in shared code (Q-14, Q-15, Q-16, Q-35).** `src/shared/review.ts` derives comments from reactions and applies the sign-off rule, from a word diff of the reviewer's text against the draft with the `diff` package, so the page preview and the server poster run the same function. The sign-off is locked on at 50% or below and removable above. Rejected: the page sending finished bodies to the server, which would let the preview and the post drift; and a character diff, which counts reformatting as authorship.
15. **The server posts, as Bitbucket drafts, after a spike (Q-16, Q-31, Q-32).** Comments are posted with `pending: true`, summary last, tasks attached to their comments, and the reviewer presses "Finish review" in Bitbucket. The API accepts `pending` but documents no way to publish drafts or to join them to the UI's review, so slice 5 starts with a spike on a scratch PR and falls back to publishing, summary last, with the page saying so. Rejected: publishing straight away without the spike, which would forgo the one-notification flow if it works; and posting from the agent, which would put the token in its context.
16. **Head check at Post, and idempotent posting (Q-17, Q-18).** Post fetches the head commit first and lets the reviewer re-anchor, drop or post anyway. Each comment records its Bitbucket id as soon as it is created and a retry sends only failures. Rejected: blocking the review whenever the head moves, which is too strict for a trivial push; and retrying the whole batch, which double-posts.
17. **Credentials read by the server only (Q-3, assumption in the write-up).** `BITBUCKET_API_TOKEN` (scope `read:pullrequest:bitbucket`) and `git config user.email` are used by the Bitbucket client and never sent to the page or agent, written to disk or logged. Rejected: asking for the token on the page, which would store it somewhere new. The error names `read:repository:bitbucket` too if the diff needs it.
18. **Bitbucket-faithful preview in a Markdown subset (Q-33).** The agent drafts only what Bitbucket renders (fenced code, tables, emphasis, lists, links; no raw HTML, task lists or suggestion blocks) and the preview renders the same subset in a Bitbucket-style card. Rejected: GitHub-style suggestion blocks, which Bitbucket has no documented API syntax for.
19. **Rounds in the same review (Q-28, Q-37, Q-38).** A moved head starts round n+1 with the worktree moved and a delta deck. Earlier comments are labelled addressed, partly, not addressed or outdated, the author's replies come from the Bitbucket thread, follow-ups are drafted and threads and tasks are resolved only after confirmation. Rejected: a new review per push, which would lose the earlier comments and replies; and resolving without confirmation, which the agent could get wrong in front of the author.
20. **The html block is sandboxed, with no network (Q-29, Q-30, Q-40).** `<iframe sandbox="allow-scripts" srcdoc>` with a CSP meta tag written ahead of the agent's HTML (`default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; font-src data:`), a reload if the frame navigates away, the skill forbidding links and the skill allowing it only for interactive visuals. It fills the slide when it is the only block. Rejected: allowing the network, which could send code out; `allow-same-origin`, which would give the frame the page's storage; and a whole-slide type only, since it can also sit among other blocks.
21. **The shareable copy reuses the per-tab export (Q-1, Q-27).** One slide per PDF page or one HTML file with illustrations inlined, step-throughs in their final state and takes as answered. Rejected: a separate export for review, which would duplicate the plan export.

22. **Found while building (implementation notes).**
    - *The live `html` frame is served, not `srcdoc`.* A browser check showed a `srcdoc` frame inherits the page's own `script-src 'self'`, so the block's script never ran. The page frames it from `api/frame/<blockId>`, which the page server answers with the same policy as a response header plus `sandbox allow-scripts`; the document still carries the policy as the first element of its head. The HTML export, which has no page policy, moves that document into the frame's `srcdoc`. Verified in Chromium: the script runs, `fetch`, the parent page and storage are blocked (see `notes/slice-7.md`).
    - *The diff is read from git, not the Bitbucket diff endpoint.* After fetching the PR's source and destination branches, the server diffs the merge base to the head locally, so finding anchors match the worktree's line numbers and the token needs only `read:pullrequest:bitbucket`. The missing-scope message still names both scopes.
    - *The sign-off is sent as `\- Claude`.* A line of its own starting "- " is a bullet list to Python-Markdown and the preview alike; escaped, both show "- Claude".
    - *Drafts are on until the spike runs.* `POST_AS_DRAFTS` in `src/shared/review.ts` holds the slice 5 spike's outcome: it is `true` per decision 15, and the page and poster both follow it.
    - *Outdated means deleted.* An earlier comment is labelled outdated only when every line it names was deleted with nothing in its place (or its file is gone); a rewritten line is left for the agent to label, so a fix reads as addressed.
    - *Re-anchoring* moves a comment to the line whose text matches its first line nearest its old place, falls back to the whole file, and to the whole PR when the file is gone.

## Risks / Trade-offs

- [API drafts do not join "Finish review"] → The slice 5 spike runs first on a scratch PR; the fallback publishes with the summary last and says so.
- [Agent-drawn SVG looks weak or cluttered] → The illustrator has a style brief, pins carry the labels, and slice 3 judges quality on real PRs.
- [A false positive is posted under the reviewer's name] → Verify pass, confidence shown, an explicit reaction per finding, and the sign-off marks agent text.
- [The preview differs from Bitbucket] → Drafts stay in the supported subset, and a test posts to a scratch PR and compares `content.html`.
- [A big PR makes the deck slow and costly] → The fixed 6 to 15 slide spine, illustrations in parallel and a progress view.
- [The html block becomes the default] → The skill allows it only for interactive visuals; the sandbox, CSP and navigation guard contain it.
- [The token leaks] → Read from the environment by the server only; never logged, stored or sent to the page or agent.
- [The PR head moves during review] → The head check at Post.
- [Defaults for prompt kinds and density are wrong] → Slice 3 tunes them on three or more real PRs, and they stay easy to change.
- [About 6k lines, with the page the largest part] → Seven slices, each ending in something usable, with tests colocated.

## Migration Plan

Review is additive. Plan and ask state files are unchanged and still load, so there is no data migration. `planroom install` registers the new server and links the new skill and agents on the next run, and `planroom uninstall` removes them. Roll out in the seven slices of tasks.md; a slice can be released alone because each leaves the earlier ones working. Rollback is removing the `planroom-review` server, skill and agents, which touches no plan or ask data.
